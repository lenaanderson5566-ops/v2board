# Browser cookie sessions

User pages and the administrative console use separate host-only HttpOnly cookies (`__Host-fastdog_user` and `__Host-fastdog_admin` in production). Cookies contain random 256-bit identifiers; credentials and synchronizer CSRF secrets reside in the existing shared cache. Server records reference the same revocable AuthService sessions used by native clients. App Bearer, subscriptions, node communication and signed payment callbacks keep their existing protocols.

Browser login/registration and App-to-browser one-time exchanges rotate the cookie and return only session metadata, never the access/subscription token. Browser-to-App approval authenticates via Cookie and creates an independent native Bearer session through PKCE. Administrator privileges are checked on every privileged request. Online logout revokes the scoped current session; offline logout queues a non-secret local revocation marker and clears UI state, and the next bootstrap must complete server revocation before restoring a session (the server cannot be revoked while offline); password changes, password recovery and account-wide revocation invalidate all source sessions. User/admin cookies do not grant each other's scoped sessions. Cookie flags do not create a security boundary against same-origin XSS; administrators should ideally use a separate origin in future deployments.

Browser requests declare `X-Browser-Client: user|admin`. Credentials in Authorization, query or auth_data body fields are ignored in browser mode. Mutations (including login and legacy migration) require `X-CSRF-Token` bound to the opaque cookie plus an exact allowed Origin. Public `GET /api/v10/auth/browser-session` initializes an anonymous ten-minute session or restores metadata/CSRF. `DELETE` revokes it. `POST` exchanges a valid legacy token from the JSON body during the transition window, revokes that old token, and rotates into a new session. The frontend deletes its old localStorage credential after successful exchange or definitive expiry/rejection; it never writes a new login token. CSRF is retained in memory only. A 419 can be retried once after refreshing bootstrap metadata, because the rejection happens before the business action; network failures are not replayed.

Authenticated cookies expire on seven days of user inactivity or twelve hours of administrator inactivity, and no later than the underlying new session's thirty-day absolute expiry. Anonymous and idle-expired cache records cannot authenticate. Existing session revocation and banned-account checks remain authoritative.

## Deployment

Deploy backend and rebuilt frontend together. Set canonical HTTPS `v2board.app_url`. Production cookies are Secure by default. Only local HTTP development may set `BROWSER_COOKIE_SECURE=false`; never use this in production. No database migration is needed for the cookie change, but retain the existing payment-removal migration.

CORS no longer reflects arbitrary origins: canonical website origin and exact `FRONTEND_ALLOWED_ORIGINS` entries are accepted; `*` does not authorize credentialed browser access. Same-origin hosting is preferred. Frontend/API subdomains must be on the same site and use HTTPS; API cookies stay host-only. Unrelated-site deployments are not supported by this SameSite=Lax design; use a same-site API gateway rather than weakening cookies to None. Configure trusted reverse proxies and restart workers using the normal deployment procedure. Do not clear shared Redis/application caches or change APP_KEY during deployment; either will invalidate sessions.

Legacy-token migration defaults to ending at 2026-10-21 00:00 UTC. Set `BROWSER_LEGACY_EXCHANGE_UNTIL` explicitly to your intended short deployment transition deadline, then disable it by setting a past date when rollout completes. Expired/revoked old tokens require normal sign-in. Do not log cookies, CSRF secrets, passwords, migration tokens or callback codes. An explicit allowed frontend origin is trusted to perform browser actions; keep the allowlist narrow.
