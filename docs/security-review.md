## 尚未解决，不能视为安全通过

### P1：部分历史支付适配器没有检查到账事件

`app/Payments/BTCPay.php::notify` 验签后读取 invoice 并直接返回订单号，未检查 webhook type 和发票结算状态。`app/Payments/Coinbase.php::notify` 同样未按事件类型区分成功、创建、失败事件。若支付商发送未到账事件，当前处理链可能把订单标记为已支付。未核实线上是否启用了这些渠道及订阅事件类型。

BTCPay 官方将 InvoiceProcessing 与 InvoiceSettled 分开，后者才允许交付：[官方集成说明](https://docs.btcpayserver.org/Development/ecommerce-integration-guide/)。建议逐支付商核对实际版本，增加到账状态、金额/币种、商户和订单归属检查及签名样例测试。共享回调目前也未统一核对返回金额与订单应付金额。此次未擅改供应商 SDK 的原生协议。

### P1：部分 USDT 适配器关闭 TLS 证书验证

`app/Payments/Epusdt.php` 和 `app/Payments/BEasyPaymentUSDT.php` 设置 CURLOPT_SSL_VERIFYPEER=0。网络被拦截时存在中间人风险。MGate 已开启证书与主机名验证。应为上述网关恢复证书校验并验证实际证书链；此轮未修改它们。

### P2：部署信任边界

- CORS 反射任意 Origin 且允许 credentials。当前网页登录依靠手动 Authorization、未启用会话 Cookie，因此不能据此直接断言可窃取登录态；应按实际前端域名设置允许列表，在引入 Cookie 前必须收紧。
- 后台/客服保留 auth_data 参数鉴权，查询参数可能被访问日志记录。前端当前使用 Authorization，建议后续停用查询参数鉴权并确认外部调用方。
- 后台自定义页脚允许脚本，是现有受信任管理功能；管理员或客服脚本一旦被攻陷可接触同源登录凭证。应严格限制管理账户、第三方客服脚本和后台访问范围。
- 订阅 token 位于 URL；应用 V10 日志记录路由模板，但 Nginx/CDN 访问日志需另行脱敏。应用代码无法保证生产代理日志和缓存策略。

## 2026-10-12 修复补充

- 客服读写仅限普通用户；详情使用允许字段列表，不再输出密码哈希、盐、订阅 token 或 UUID。修改密码、邮箱或封禁时撤销目标用户登录会话。
- 客服批量封禁、邮件补齐经过验证的筛选条件，并强制排除管理员与客服；不允许以密码或凭据作为筛选字段。
- 支付回调核对订单所选渠道，历史快照保留已发起支付渠道的合法延迟回调。EPay、Paytaro、StripeCheckout 必须提供与订单及手续费一致的金额；缺失或不符拒绝入账。
- StripeCheckout 遵循当前 CNY-only 约束，不再通过实时汇率创建外币支付；现有非 CNY 配置需改为 CNY，历史外币未结订单需人工核对处理。未付款及无关的已验签事件仅应答、不入账。
- 其他支付适配器仍需逐一按供应商协议验证金额与币种；本补充不表示所有支付商均完成了金额校验。
- 新增 tests/audit-security-regression.php，使用本地事务回滚与队列替身，覆盖越权、凭据泄露、筛选、会话撤销及签名回调。上述旧审计记录保留为历史，不代表当前依赖版本状态。

## 后端检查记录（2026-10-08）

### 已复现并修复

#### 佣金划转并发不一致

`UserActions::transfer` 原先在事务外读取用户余额。两个请求同时使用同一份佣金余额时都返回成功，生成两条划转记录，但余额只增加一次；与其他余额更新并发时还存在覆盖新余额的风险。

修复：在带重试的数据库事务中锁定用户行，读取并校验最新佣金余额，原子保存用户及划转记录。

验证：修复前两个请求均成功且有两条记录；修复后仅一个成功，另一个返回 409，只产生一条记录。另模拟同时入账 500 分，划转 1000 分后余额为 1500 分，佣金为零。

#### 负数套餐价格被视为免费订单

后台八种套餐价格字段原先允许负整数，下单未拒绝负价，结账把所有非正数都作为免费订单处理。触发前提是管理员配置或历史数据含负价；不是普通用户能够直接修改服务端套餐价格。

修复：后台价格最小值为零，下单拒绝未配置或负价周期，结账拒绝历史负数订单。明确设置为零的合法免费订单仍可支付。

验证：八种价格分别测试负数、null、零和正数；负价无法创建订单，历史负数订单不能转为已支付，零元订单仍进入支付处理。

#### Telegram 回调在未配置令牌时认证不安全

原逻辑直接计算配置令牌的摘要，空令牌产生可预测的校验值；此外停用机器人并不拒绝回调。验证了构造回调处理器时认证被接受，未执行伪造消息或向 Telegram 发送请求。具体业务影响还取决于保留的绑定信息和可触发命令。

修复：机器人必须启用且令牌非空，之后才比较回调凭据。V10 继续使用请求头，旧入口继续使用原参数，不改变已配置机器人的签名协议。
