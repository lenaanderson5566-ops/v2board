# 系统业务时区与界面显示时区

## 设置与显示

- 后台「系统配置 → 站点」的「系统业务时区」使用 IANA 名称，例如 `Asia/Shanghai`、`America/New_York`。默认上海；保存后后台自动刷新。它控制业务日期输入、每日任务和相应报表日界线，不修改操作系统时区。
- 后台右上角「账户菜单 → 界面显示时区」提供跟随业务时区（默认）、跟随设备及指定时区。它是当前管理员、站点/API 地址和浏览器隔离的非敏感界面偏好，不写用户账户偏好或系统配置，不跨设备同步；存储不可用时提示仅本次打开期间生效。订单、日志、入口检查和报告生成等事件按界面时区换算，页面同时标明业务时区。切换时原地重绘，保留表单草稿，不额外请求数据。
- 后台日期输入、排期和筛选始终使用业务时区；输入控件与说明不随显示偏好移动。统计区间及日汇总保留报表声明的业务/UTC 口径和原有分桶，不按界面时区重新划分日期。界面时区不影响流量重置、到期、计费、导出或定时任务。退出或切换管理员时先清除当前生效偏好，再按新账户加载。
- 用户网站的账户偏好、FastAI 账户页可选择展示时区，或跟随设备。偏好保存在账户中，多端共享；跟随设备时各设备使用自己的本地时区。
- 用户网站中的到期、重置、订单与付款、优惠券有效期、公告与工单、安全会话、配置更新、下载账户检查和 Telegram 链接等事件时刻统一按个人显示时区转换；没有偏好时跟随设备。显示时区和语言分别决定时间换算与日期格式。界面中需要显示偏移时采用简短标记，如 `UTC+8`、`UTC-4`、`UTC+5:45`，零偏移显示 `UTC`；半小时和四分之一小时偏移保留分钟。不混用 GMT、EST、EDT 或翻译后的时区缩写。偏移按所展示事件的日期计算，订阅到期显示到分钟，时区标记放在日期时间末尾；诊断和安全记录保留秒，已在上下文标明时区的选择器预览可以省略重复标记。到期、订单、日志等实际时刻继续保存 Unix 时间戳，V10 API 返回 UTC ISO 8601。修改显示时区不会修改套餐到期时刻。FastAI 的指定时区显示由后端生成，跟随设备时由设备转换；旧后端缺少格式化字段时明确回退显示 UTC。
- 后台日期输入按系统业务时区转换，不使用浏览器时区；编辑器、日志筛选、公告排期、维护截止和 FastAI 发布时间均保留秒。未改动的已有时刻保留原始时间戳，包括夏令时回拨时重复出现的本地时间；新选或实际修改为跳过、重复的本地时间仍拒绝保存，要求选择无歧义时刻。FastAI 发布时间提交继续使用 UTC ISO 8601。
- 自动重置的实际时刻由业务时区和套餐规则决定。网站只展示换算到个人显示时区的日期时间，末尾带单个简短 UTC 偏移，不重复展示系统时间。例如上海每月 1 日 00:00，在 UTC 下显示前一天 16:00，仍是同一次重置。偏移按目标时刻计算，不能固定为当前夏令时偏移。
- 订阅客户端的信息节点使用已保存的用户展示时区；未保存或跟随设备时，由于订阅请求无法可靠取得设备时区，明确使用业务时区并同时显示 IANA 名称与 UTC 偏移。它不会猜测设备时区，也不以偏移代替 IANA 配置。
- 流量日统计属于日期区间而非单个事件时刻，按系统业务日汇总，图表使用简短说明标出统计时区；不能把已经汇总的一天准确重分成另一时区的一天。用户流量明细保留记录生成时的时区及业务日期（旧记录沿用原固定上海时区），切换系统业务时区不会把旧记录移到前一天。历史汇总不重算，跨切换点的报表仍需按原统计口径理解；建议在业务低峰调整。用户展示时区不会改变日统计分组。
- Telegram 免打扰和日期使用用户指定时区。选择跟随设备时，机器人使用系统业务时区并在设置中说明，因为机器人无法取得设备时区。三天宽限仍为 72 小时。
- 用户订单、优惠券、公告、工单和佣金等常规记录显示到分钟；安全会话、配置请求、下载账户检查和短期授权链接保留秒。工作区标题日期在个人时区跨日或页面重新可见时刷新，不额外读取账户数据。后台统一提示界面和业务时区，表格行内不重复添加时区后缀；安装包上传、入口检测等事件统一换算，统计图表轴保留原口径，缺失的节点上报时间不显示为 1970 年。
- 共享事件格式器只接受有效 Unix 秒、Date 或带明确时区的 ISO 时间；空值、非法日期和无时区字符串显示占位符，不由浏览器猜测时区。日期型统计区间和时长继续按各自的业务口径处理。
- 后台优惠券和礼品卡 CSV 的起止、创建时间使用含秒和明确数字偏移的 ISO 8601，例如 `2026-11-01T01:30:37-04:00`。列名、列数、顺序和无期限的空单元格保持不变；外部处理脚本应按 ISO 8601 读取，不再依赖无时区的日期文本。导出按系统业务时区计算目标时刻偏移，不依赖 PHP 默认时区。

## 时区选择器

网站、后台和 FastAI 默认展示常用城市，保留当前选择，通过“更多时区”搜索其他 IANA 名称。用户和后台界面显示偏好可选择跟随设备；后台的系统业务时区不提供该选项。网站展示实时当地时间；FastAI 使用后端提供的打开时预览和当时 UTC 偏移，明确标注预览时间。偏移由时区规则计算，不作为存储值；夏令时仍由原 IANA 时区处理。旧后端没有预览数据时，App 仍允许选择时区，但不猜测偏移。

后台实际更改业务时区时，保存前显示原/新 IANA 时区、同一时刻的两地时间以及对重置日期、报表日界线和每日任务的影响，要求明确勾选确认。确认绑定当前原/新值，改回原值后再选择或更换目标时区均需重新核对；设置读取失败时不能确认保存。普通配置修改不增加此确认。保存继续复用原设置接口，不迁移历史时间戳或重放重置记录。

## 每日任务

`system:daily` 每分钟检查业务日期和本地时间，达到计划时间后执行；通常在目标分钟运行，实际延迟取决于 cron、队列和负载。

| 任务 | 业务本地时间 |
| --- | --- |
| 流量重置、旧流量日志清理 | 00:00 |
| 昨日统计 | 00:10 |
| 邮件提醒 | 11:30 |
| 自动续费检查 | 22:30 |

数据库按任务和业务日期保存状态，配合分布式锁避免同日重复执行。夏令时回拨不会再次执行已完成日期；跳时或短暂调度延迟后，会在当日下一次检查补执行。失败保留状态，至少五分钟后重试。流量重置额外在同一事务中保存每用户/业务日期记录，避免部分失败后再次清空已重置用户的新流量。

重置信息查询使用相同业务时区和到期规则，并只读核对当天任务及本人重置记录。当天应重置但任务缺失或运行中时返回 `pending`，失败时返回 `failed`；界面保留本次应执行时刻，显示待确认/待重试，不直接跳到下一周期。本人记录完成后即可显示后续日期，即使其他用户仍需重试；当天任务已完成或为升级保护状态时显示后续日期。此查询不清零、不写任务记录、不触发重试。V10 `resetState` 为可选、可空字段，`resetAt` 始终为 UTC ISO 8601：在待处理状态下允许表示已经到达的应执行时刻。

这不是跨停机日的补账系统：整日离线后不会自动重放多日清零、邮件或续费。需要人工核对遗漏日期。也不承诺外部邮件发送等副作用的严格 exactly-once。

## 部署与核查

1. `update.sh` 已加入 `2026_10_13_000007_add_timezones.php` 迁移。手工部署须执行该迁移，并部署前端构建产物。
2. 首次升级时，当天已经到达执行时间的任务标记 `skipped_upgrade`，防止旧调度已经执行过后再次清零；尚未到时间的任务照常执行。这个标记不表示旧任务已被验证成功，升级当天应检查旧执行日志。
3. 保持 cron **每分钟**调用 `php artisan schedule:run`。不要额外保留独立的 `reset:traffic` 等旧 cron 条目。多实例须共享数据库和支持锁的缓存。
4. 部署后重启 Horizon/常驻队列进程以加载新代码；新代码在每次处理队列任务前重读业务时区。仅修改时区后无需人工重启这些已升级的进程。
5. 执行只读命令 `php artisan system:daily-status`，核对当前业务时间、当天任务状态及更新时间。午夜后应看到重置任务 `completed`；`pending` 长时间不变化需检查 cron/锁，`failed` 需检查系统日志。
6. `tests/timezones.php` 验证多个时区、夏令时及重置日期计算；`tests/timezone-scheduler.php` 只在 local 环境使用独立内存数据库和虚拟任务验证重复保护、失败退避与重试，不执行真实清零任务。

本地验证不能代替生产 cron 的实际运行检查；部署后应在所选业务时区跨过一次午夜后核查状态。
